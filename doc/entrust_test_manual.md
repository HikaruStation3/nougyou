## 0. 先看懂业务，再谈测试

### 0.1 一句话业务模型

**A 农户（委托方）把自己名下的商品交给 B 农户（受托方）在自己的店铺代卖，卖出后按约定比例分钱，平台按月出结算单。**

一条委托关系有 4 个状态，只有「生效中」才真正产生代销行为：

```
                    ┌── confirm(agree=true) ──► 1 生效中 ── terminate ──► 2 已终止
0 待确认 ───────────┤
                    └── confirm(agree=false) ─► 3 已拒绝

0 待确认 ── terminate ──► 2 已终止          （委托方后悔，可直接撤）
2 已终止 / 3 已拒绝 是终态，不能再确认、不能再终止
```

### 0.2 业务主线（答辩演示就按这条走）

```
① 委托方建立委托(087) → ② 受托方确认(091) → ③ 商品进入代销
        ↓
④ 买家下单该商品(订单模块 052)：订单归属受托方，order_item.entrust_id 记录委托关系
        ↓
⑤ 买家支付(055) → ⑥ 统计接口(093) 立刻能看到销量/销售额/双方分成
        ↓
⑦ 管理员生成月度结算单(095) → ⑧ 双方查看结算单(094)
```

**这条链路是模块的核心**：委托关系不直接产生金额，金额来自"挂在 entrust_id 上的已支付订单"，再由视图 `v_entrust_sale_stat` 汇总。

### 0.3 三条硬规则（测试必须验证，也是最容易出错的地方）

| 规则 | 说明 | 违反后的现象 |
|---|---|---|
| 一个商品同时只能有 **1 条** 待确认或生效中的委托 | 087 创建时校验；下单时 `findSingleActiveEntrust` 还要求「生效中的数量 = 1」 | 同一商品挂 2 条生效委托时，**下单不归受托方、统计全是 0**（已实测复现） |
| 统计只认「已支付 + 未取消」的订单 | 视图口径 `pay_status = 1 AND order_status <> 4` | 未支付/已取消订单不下账；退款只认售后 `status = 2` |
| 结算金额按**净额**分成 | 净额 = 销售额 − 退款额；受托方 = 净额 × 分成%；委托方 = 净额 − 受托方 | 只减受托方分成、不减退款，会算错账 |

## 4. 逐业务测试

### 4.1 业务一：建立委托关系（API-087）

**业务含义**：委托方选定自己的一个商品 + 一个其他农户，约定分成比例、结算周期、有效期，提交后进入「待确认」，此时还没有任何代销效果。

**页面怎么点**

1. 3100 门户登录 `farmer02`（密码 + 验证码）→ 右上角头像 → **委托销售**。
2. 右上「建立委托关系」→ 弹窗依次选：被委托商品（只列自己店铺商品）、受托方（只列其他农户，带店铺名）、受托方分成（默认 20%）、结算周期、生效开始/结束、约定说明。
3. 点「提交」。

**接口怎么调**

```bash
curl -s -X POST http://localhost:8081/api/v1/entrusts \
  -H "Authorization: Bearer $FARMER02" -H "Content-Type: application/json" \
  -d '{"agentUserId":4,"productId":4,"splitRatio":15,"settleCycle":1,
       "startDate":"2026-11-26","endDate":null,
       "agreementDesc":"接口测试：土蜂蜜委托吴叔代销"}'
```

| 参数 | 必填 | 约束 |
|---|---|---|
| `agentUserId` | 是 | 必须是 FARMER 角色，不能是自己，必须存在 |
| `productId` | 是 | 必须是**自己名下**的商品，且当前没有待确认/生效中的委托 |
| `splitRatio` | 是 | 0 ~ 100，两位小数；受托方拿这个比例，委托方拿剩余 |
| `settleCycle` | 是 | 1 按月 / 2 按季 / 3 按单（**以接口和前端为准，DDL 注释是反的**，见 7.1） |
| `startDate` | 是 | `yyyy-MM-dd` |
| `endDate` | 否 | 不能早于 `startDate`；留空表示长期 |
| `agreementDesc` | 否 | ≤ 500 字 |

**✅ 通过判据（全部满足才算过）**

1. HTTP 200，`code = 00000`。
2. 返回体 `status = 0`（待确认），`confirmTime = null`。
3. `entrustNo` 形如 `WT` + `yyyyMMdd` + 4 位数字，例如 `WT202611266323`。
4. `entrustUserName` / `agentUserName` / `productName` 三个人名商品名都能回填，不是 null。
5. 列表校验：委托方在 `sent` 第一条能看到它；受托方在 `received?status=0` 能看到它。
6. 受托方在「我代销的」里看到的是 **待确认** 标签，并且出现「接受 / 拒绝」按钮。
7. 再提交一次同商品 → `A0400 该商品已有待确认或生效中的委托关系，请先终止后再委托`。

**反向用例（逐条断言）**

| 输入 | 预期 |
|---|---|
| `agentUserId` = 自己 | `A0400 不能委托给自己` |
| `agentUserId` = 1（买家） | `A0400 受托方必须为已认证的农户商家` |
| `agentUserId` = 9999 | `A0400 受托方不存在` |
| `productId` = 9999 | `A0400 被委托商品不存在或已删除` |
| `productId` = 别人的商品（farmer02 传 6） | `A0301 只能委托自己名下的商品` |
| 不传 `productId` | `A0400 被委托商品不能为空` |
| `splitRatio` = 120 | `A0400 分成比例不能大于 100` |
| `settleCycle` = 5 | `A0400 结算周期取值为 1-3` |
| `endDate` < `startDate` | `A0400 生效结束日期不能早于开始日期` |
| `agreementDesc` 501 字 | `A0400 约定说明最长 500 个字符` |
| 买家 token 调用 | HTTP 403 + `A0301 权限不足` |

**实测记录**

```
POST /entrusts (farmer02, product 4 → farmer01, 15%, 按月)
→ 00000，id=10，entrustNo=WT202611266323，status=0，confirmTime=null
同商品再建 → A0400 该商品已有待确认或生效中的委托关系，请先终止后再委托
```

### 4.2 业务二：委托方 / 受托方两个列表（API-088 / 089）

**业务含义**：同一条委托关系，在委托方眼里是"我委托出去的"，在受托方眼里是"我代销的"。两个接口查的是同一张表，只是过滤字段不同（`entrust_user_id` vs `agent_user_id`）。

**页面怎么点**：委托销售页 → 两个 Tab 来回切；状态下拉选「待确认 / 生效中 / 已终止 / 已拒绝」→ 查询；底部分页改每页条数。

**接口**

```bash
curl -s -H "Authorization: Bearer $FARMER03" \
  "http://localhost:8081/api/v1/entrusts/sent?pageNum=1&pageSize=10&status=1"
curl -s -H "Authorization: Bearer $FARMER01" \
  "http://localhost:8081/api/v1/entrusts/received?pageNum=1&pageSize=10"
```

**✅ 通过判据**

1. `sent` 只出现 `entrustUserId = 当前登录用户` 的记录；`received` 只出现 `agentUserId = 当前用户` 的记录。
2. 两个接口对**同一条**关系的 `id` / `entrustNo` / `splitRatio` / `status` 完全一致（同一份数据，双向可见）。
3. `status` 过滤生效：`status=1` 的结果全部是「生效中」。
4. 默认按创建时间倒序，最新建的排第一。
5. `pageSize=1000` 时实际最多返回 100 条（代码 `MAX_PAGE_SIZE = 100`）。
6. 用第三个农户登录，两个列表都**看不到**别人的关系。
7. 买家调用 → HTTP 403（没有 `entrust:list`）。

**实测记录**

```
farmer03 /sent?status=1 → total=3，全部 status=1
farmer01 /received?status=0（测试中）→ 命中 id=10「百花土蜂蜜」
```

### 4.4 业务四：受托方确认 / 拒绝（API-091）

**业务含义**：待确认的关系只有受托方能拍板。接受 → 立即生效；拒绝 → 关系作废，拒绝原因追加进约定说明，供委托方查看。

**页面怎么点**

1. 登录 `farmer01` → 委托销售 → Tab「**我代销的**」→ 状态选「待确认」。
2. 点「接受」→ 确认框 → 确定；或点「拒绝」→ 输入原因（必填）→ 确定。
3. 切到委托方账号（farmer02）→「我委托出去的」→ 看状态是否变为「生效中 / 已拒绝」。

**接口**

```bash
# 接受
curl -s -X PUT http://localhost:8081/api/v1/entrusts/10/confirm \
  -H "Authorization: Bearer $FARMER01" -H "Content-Type: application/json" \
  -d '{"agree":true}'

# 拒绝
curl -s -X PUT http://localhost:8081/api/v1/entrusts/10/confirm \
  -H "Authorization: Bearer $FARMER01" -H "Content-Type: application/json" \
  -d '{"agree":false,"remark":"近期仓库已满"}'
```

**✅ 通过判据**

接受：

1. `status` 由 `0` → `1`，`confirmTime` 写入当前时间。
2. 若原 `startDate` 为空，会自动补成今天（当前样本都有开始日，不受影响）。
3. 委托方的 `sent` 列表刷新后显示「生效中」，行内「接受/拒绝」按钮消失。
4. 该商品从此刻起进入"可代销"状态 —— 下单才会归受托方（见 4.9）。

拒绝：

1. `status` 由 `0` → `3`，`confirmTime` 仍为 null。
2. `agreementDesc` 末尾追加 `；[受托方拒绝] 近期仓库已满`。
3. 页面上该行状态标签变红「已拒绝」，委托方也看到同一段拒绝原因。
4. 该商品释放，可以重新发起委托（不再报"已有待确认或生效中"）。

**反向用例**

| 输入 | 预期 |
|---|---|
| 委托方自己确认 | `200 + A0301 只有受托方可以确认该委托` |
| 已确认过的再确认 | `200 + A0400 该委托关系已处理，无需重复确认` |
| 已拒绝的再确认 | 同上 |
| `agree` 不传 | `A0400 请选择是否接受委托` |
| `remark` > 200 字 | `A0400 说明最长 200 个字符` |

**实测记录**

```
farmer01 接受 #3 → status=1，confirmTime=2026-11-26 21:48:32
```

### 4.5 业务五：终止委托（API-092）

**业务含义**：双方任意一方（或管理员）都可以提前结束合作。终止后：状态封存、结束日改为今天、原因写入备注；**历史订单仍计入统计，新订单不再挂这条关系**。

**页面怎么点**：委托销售 → 任一 Tab → 状态为「待确认」或「生效中」的行 →「终止」→ 填原因（可留空）→ 确定。

**接口**

```bash
curl -s -X PUT http://localhost:8081/api/v1/entrusts/11/terminate \
  -H "Authorization: Bearer $FARMER02" -H "Content-Type: application/json" \
  -d '{"reason":"商品季节性下架，暂停代销"}'
```

**✅ 通过判据**

1. `status` → `2`（已终止），`endDate` 改写为**今天**（即使原有效期是明年）。
2. 传了 `reason` 时，`agreementDesc` 追加 `；[终止] 商品季节性下架，暂停代销`。
3. 页面上「终止」按钮消失，状态标签变灰「已终止」。
4. 该商品可以重新发起新委托（旧的已终止不占用）。
5. 不传请求体也能成功（`form` 允许为空）—— 实测 `PUT /entrusts/13/terminate` 无 body 返回 `00000`，`status=2`。

**反向用例**

| 输入 | 预期 |
|---|---|
| 已终止的再终止 | `A0400 该委托关系已结束，无需重复终止` |
| 已拒绝的再终止 | 同上 |
| `reason` > 200 字 | `A0400 终止原因最长 200 个字符` |
| 第三方农户终止 | `200 + A0301 无权访问该委托关系` |

**实测记录**

```
新建 #11（10%）→ farmer01 接受(status=1) → farmer02 终止 → status=2，endDate=2026-11-26
再次终止 → A0400 该委托关系已结束，无需重复终止
```

### 4.6 业务六：委托销售统计（API-093）

**业务含义**：委托方和受托方看**同一份**销售数据 —— 卖了多少件、卖了多少钱、退了多少、各自该分多少。数据源是数据库视图 `v_entrust_sale_stat`，不是实时 SQL 拼装，所以**双方读数天然一致**。

**页面怎么点**：委托销售 → 行内「统计」→ 弹窗「委托销售统计」，12 个字段一次显示。

**接口**

```bash
curl -s -H "Authorization: Bearer $FARMER03" \
  http://localhost:8081/api/v1/entrusts/3/stat
```

**字段口径（判定的关键）**

| 字段 | 来源 | 口径 |
|---|---|---|
| `stock` | `product.stock` | 当前库存（不是代销库存） |
| `totalSaleCount` | `product.sale_count` | **商品全渠道累计销量**，不等于代销销量 |
| `saleQty` / `saleAmount` | `order_item` | 该关系下「已支付 + 未取消」订单的件数/金额 |
| `refundQty` / `refundAmount` | `after_sale` | 只算售后 `status = 2`（已完成）的退单 |
| `entrustIncome` | 计算 | `(销售额 − 退款) × (100 − 分成%) / 100` |
| `agentIncome` | 计算 | `(销售额 − 退款) × 分成% / 100` |

**✅ 通过判据**

1. 委托方与受托方调用**同一个 id**，返回的 12 个字段**逐字段完全一致**（实测双方都是 `2 / 84.0 / 58.8 / 25.2`）。
2. 分成校验：`entrustIncome + agentIncome = saleAmount − refundAmount`（误差 ≤ 0.01）。
3. 比例校验：`agentIncome / 净额 = splitRatio / 100`。
4. 未支付订单**不改变** `saleQty`（下单不支付，统计仍是原值）。
5. 取消的未支付订单**不改变**统计（库存回滚，销量不动）。
6. 第三方农户调用 → `200 + A0301 无权访问该委托关系`；买家 → 403。

**实测记录（本次代销链路，entrust 3 / 商品 9，分成 30%）**

```
下单前：stock=25, totalSaleCount=31, saleQty=0,   saleAmount=0,   entrustIncome=0,     agentIncome=0
下单 2 件并支付：saleQty=2, saleAmount=84.0, entrustIncome=58.8, agentIncome=25.2, stock=23
委托方 farmer03 与受托方 farmer01 读数完全一致
另一笔「下单 1 件未支付」→ 统计仍为 2 / 84.0（未支付不计）
取消该笔 → 统计不变，库存回到 23
```

### 4.8 业务八：后台生成月度结算单（API-095）

**业务含义**：管理员选定某条委托关系 + 某个月份，系统把该月「已支付订单 − 已完成退款」汇总，按分成比例拆成两笔应得金额，落一条结算单。**同一关系同一月份只能生成一次**。

**页面怎么点**

1. 3000 管理端登录 `admin` → 左侧「系统管理」→「**委托结算**」。
2. 列表可按委托编号 / 商品名搜索，按状态筛选。
3. 目标行点「生成结算」→ 弹窗显示委托编号、商品、委托关系、分成比例 → 选月份（默认当月）→「生成结算单」。
4. 弹「2026-11 结算单已生成」→ 再点「结算记录」能看到这一条。

**接口**

```bash
# 后台选关系
curl -s -H "Authorization: Bearer $ADMIN" \
  "http://localhost:8081/api/v1/admin/entrusts?pageNum=1&pageSize=10"

# 生成
curl -s -X POST http://localhost:8081/api/v1/admin/entrusts/3/settle \
  -H "Authorization: Bearer $ADMIN" -H "Content-Type: application/json" \
  -d '{"settleMonth":"2026-11"}'
```

**✅ 通过判据**

1. `code = 00000`，返回的 `saleQty` / `saleAmount` / `refundQty` / `refundAmount` 与同期统计接口的数值一致。
2. 金额拆分正确：`agentIncome = 净额 × 分成%`，`entrustIncome = 净额 − agentIncome`。
3. `status = 1`（已结算），`settleTime` 为当前时间。
4. `entrustId` 之外还带 `entrustNo`、`productName`，页面不用二次查询。
5. 重复生成同月 → `A0400 该委托关系 2026-11 的结算单已生成，请勿重复结算`。
6. 生成后，商家侧「结算单」弹窗立刻能看到这条（同一张表）。
7. 管理端列表按 `keyword` 搜委托编号、商品名都能命中（实测「收纳篮」「WT202611050003」各命中 1 条）。

**反向用例**

| 输入 | 预期 |
|---|---|
| `settleMonth = "2026-13"` | `A0400 结算月份格式应为 yyyy-MM` |
| `settleMonth = ""` | `A0400 结算月份不能为空` |
| 商家 token 调用 | HTTP 403 + `A0301 权限不足` |
| 不存在的委托 id | `A0404 委托关系不存在` |

**实测记录**

```
POST /admin/entrusts/3/settle {"settleMonth":"2026-11"}
→ id=8, saleQty=2, saleAmount=84.0, refundQty=0, refundAmount=0.0,
  entrustIncome=58.8, agentIncome=25.2, status=1, settleTime=2026-11-26 21:49:35
重复 → A0400 该委托关系 2026-11 的结算单已生成，请勿重复结算
```

### 4.9 业务九（跨模块）：代销商品成交如何进入统计

**这是整个模块最值钱的一条链路，答辩必演。** 它验证的不是委托接口，而是「委托关系 → 订单归属 → 统计 → 结算」的贯通。

**业务规则**：商品存在**唯一一条**生效中的委托时，买家下单会把订单的 `farmer_id` 改成**受托方**，并给 `order_item.entrust_id` 打上关系 ID。受托方在自己的「商家订单」里发货，销售额自然落进这条委托的统计。

**操作步骤**

1. 先用 4.4 把一条委托确认成「生效中」（本次用 #3：蔡伯 → 吴叔，商品 9，30%）。
2. `buyer01` 在 3100 门户买「手工竹编收纳篮」2 件，提交订单（先不支付）。
3. 看订单详情 / 返回体：商家应显示 **绿野农场（吴叔山货铺）**，不是蔡伯；明细旁有「委托代销」标记。
4. 支付该订单。
5. `farmer01` 打开委托销售 → #3「统计」：`saleQty` +2、`saleAmount` +84、双方分成同步变化。
6. `farmer03`（委托方）看同一条统计：数字完全一样。

**接口**

```bash
# 下单
curl -s -X POST http://localhost:8081/api/v1/orders \
  -H "Authorization: Bearer $BUYER01" -H "Content-Type: application/json" \
  -d '{"source":"buyNow","productId":9,"quantity":2,
       "receiverName":"沈明","receiverPhone":"13800138000",
       "receiverAddress":"莆田市仙游县钟山镇湖亭村3号","payType":3}'

# 支付
curl -s -X PUT http://localhost:8081/api/v1/orders/61/pay \
  -H "Authorization: Bearer $BUYER01" -H "Content-Type: application/json" \
  -d '{"payType":3}'

# 统计
curl -s -H "Authorization: Bearer $FARMER01" \
  http://localhost:8081/api/v1/entrusts/3/stat
```

**✅ 通过判据**

1. 下单返回 `data` 是数组；`data[0].farmerId = 4`（受托方），`shopName = 绿野农场`。
2. `data[0].items[0].entrustId = "3"`（自营商品此处为 null）。
3. 下单前可先查 `GET /api/v1/products/9`：返回 `entrustId = "3"` 说明该商品处于代销；但 `shopName` 仍是原主「云岭茶庄」，商品页不会改成受托方。
4. 下单后统计**不动**（`pay_status=0`）；支付后 `saleQty` 才 +2。
5. 支付后：`saleAmount = 2 × 42 = 84`，`agentIncome = 84 × 30% = 25.2`，`entrustIncome = 58.8`。
6. 委托方与受托方读数一致。
7. 商品库存：下单时 −2（预占），取消时回滚。
8. 受托方「商家订单」能看到这张单并能发货（订单归属已改）。

**两条反例（必须测，都是真实坑）**

| 场景 | 预期 | 说明 |
|---|---|---|
| 商品 7 有 **2 条**生效中的委托，下单 1 件 | `farmerId = 6`（商品原主蔡伯），`entrustId = null`，统计不动 | 系统要求"唯一生效"，多条时**完全不代销**。实测确认 |
| 商品 4 只有 1 条**待确认**委托，下单 1 件 | `farmerId = 5`（原主秀兰），`entrustId = null` | 待确认不生效，必须确认后才代销。实测确认 |

### 4.10 商品侧：测试期间对商品做什么、会变什么

委托销售的测试对象是"关系"，但所有结果都落在"商品"上。商品侧只需要做三件事：**选对、别乱改、验变化**。

**① 选品：三条硬条件（缺一不可）**

| 条件 | 怎么确认 | 不满足的后果 |
|---|---|---|
| 商品属于当前登录农户 | `GET /products/{id}` 的 `farmerId` = 当前 userId | 087 报 `A0301 只能委托自己名下的商品` |
| 商品当前没有待确认/生效中的委托 | 第 3 节表格，或 `GET /admin/entrusts?keyword=商品名` | 087 报 `A0400 已有待确认或生效中的委托关系` |
| 商品处于上架状态 | `shelfStatus = 1` | 委托能建成功（087 不校验上架），但买家下单报「已下架，无法下单」，等于演示不了成交 |

> 第三条是个业务空隙：**下架商品可以建委托、可以确认生效，但永远卖不出去**。测试时如果只测到"确认生效"就收工，会漏掉这个坑。

**② 测试期间不要对商品做的四件事**

| 不要做 | 原因 |
|---|---|
| 改价格 | 订单按**下单时**的价格快照计金额，改价只影响改价后的新订单，统计里会新旧价混在一起，对不上账 |
| 改库存（手工调） | 库存变化是判定"下单预占 / 取消回滚"的唯一证据，手工改过就说不清了 |
| 删除商品 | 统计视图是 `entrust_sale JOIN product` 内连接，商品没了这条关系查统计会直接 `A0404 委托统计不存在` |
| 给已有两条生效委托的商品下单 | 见 7.2，订单不归受托方，统计不动，看起来像 bug |

**③ 商品数据的变化时序（判定就看这张表）**

| 操作 | `stock` 库存 | `sale_count` 累计销量 | 统计 `saleQty` |
|---|---|---|---|
| 建立委托 / 确认 | 不变 | 不变 | 不变 |
| 买家下单 | **−N（预占）** | 不变 | 不变（未支付） |
| 买家支付 | 不变 | 不变 | **+N** |
| 受托方发货 | 不变 | **+N** | 不变 |
| 取消未支付订单 | **+N（回滚）** | 不变 | 不变 |

> 注意支付后的一小段时间：统计已经 +N，商品累计销量还是旧值 —— 因为 `sale_count` 是**发货时**才累加的。两个数字不一致是正常的，别当 bug 报。

**④ 每个阶段用哪个接口验商品**

```bash
# 建委托前：确认归属、上架、是否已在代销（entrustId 有值 = 代销中）
curl -s -H "Authorization: Bearer $FARMER02" http://localhost:8081/api/v1/products/4

# 下单前后：比对 stock
curl -s -H "Authorization: Bearer $BUYER01" http://localhost:8081/api/v1/products/9

# 发货后：比对 saleCount
```

**⑤ 当前库里每个商品该怎么用（照这个分工，不会互相干扰）**

| 商品 | 在测试里的角色 | 建议操作 |
|---|---|---|
| 4 百花土蜂蜜 | **主线样本** | 建委托 → 接受 → 下单 1 件 → 支付 → 看统计 → 生成结算 → 终止 |
| 9 手工竹编收纳篮 | **现成代销样本** | 不用建关系，直接下单 2 件 → 支付 → 看统计变化 |
| 3 土鸡蛋 / 8 绿茶 | 备用空闲品 | 只测"建立委托成功 + 列表可见"，测完终止掉 |
| 7 蔡伯地瓜干 | **反例样本** | 只用来验证"两条生效委托 → 不代销"，不要拿它讲正常代销 |
| 2 山茶油 / 6 笋干 | 已占用 | 用来验证"重复创建被拦"的反例，不要再建新委托 |

### 剧本 B：拒绝分支

1. farmer02 建立商品 4 → farmer03，20%。
2. farmer03 拒绝，原因填「近期人手不足」。
3. 断言：`status=3`；`agreementDesc` 末尾有 `[受托方拒绝] 近期人手不足`；farmer02 能看见这段原因。
4. 再用商品 4 建立新委托 → 应成功（被拒的不占用）。

### 剧本 C：终止与"不再代销"

4. 统计不再增长（历史值保留）。

> 第 3 步是"终止真的生效了"的最强证据 —— 只改状态标签不算。

## 7. 已知偏差与六个坑

### 7.1 结算周期的数字含义，DDL 注释和代码是反的

| 来源 | 1 | 2 | 3 |
|---|---|---|---|
| 表注释 `entrust_sale.settle_cycle` | 按单 | 按月 | 按季 |
| 接口 DTO / 前端页面 | **按月** | **按季** | **按单** |

以**接口和页面**为准。写论文/答辩时按"1 按月、2 按季、3 按单"，别照抄 DDL 注释。

### 7.2 同一商品挂两条生效委托 → 代销完全失效

商品 7 现在是 `#1 25%` + `#2 20%` 两条都生效。此时下单：

- 订单归**商品原主**（蔡伯），不是任何受托方；
- `entrust_id = null`，两条统计都不会增加。

原因是 `findSingleActiveEntrust` 的 SQL 要求「该商品生效中的委托数 = 1」。这是设计上的保护（避免分账歧义），但**种子数据本身违反了它**。演示时不要拿商品 7 讲"代销归受托方"，会被打脸。

### 7.3 生成结算不校验结算周期

按季（`settleCycle=2`）或按单（`=3`）的委托，管理员照样可以按月生成结算单，系统不拦。属于规则缺失，测试时不算 bug，但答辩被问到要能解释：「当前实现按月汇总，周期字段仅作约定展示」。

### 7.4 结算单一生成就是「已结算」

`settle()` 里直接写 `status = 1`，没有"待结算 → 已结算"的流转。所以页面上的「待结算」标签只可能来自手工插库的种子数据（如 `entrust_settlement` 里 `status=0` 的 4 条），正常流程生成的全是「已结算」。如果需要演示两种状态，得直接改库。

### 7.5 「统计」页的 `totalSaleCount` 不是代销销量

它取的是 `product.sale_count`（商品全渠道累计销量，含自营）。真正的代销销量是 `saleQty`。两个数字并排显示，容易被误读成"统计错了"。

### 7.6 拒绝后不能再终止，也不能"复活"

`terminate` 对 `status=3`（已拒绝）直接报 `A0400 该委托关系已结束`。要重新合作只能新建一条。这是刻意的，测试时不要当 bug 提。

另外两个操作层面的坑：

- 建立委托弹窗的「被委托商品」下拉**不会**过滤掉已占用的商品，选完提交才报错。演示时先看第 3 节表格，别在弹窗里试错。
- 门户和管理端都走 8080，**每次登录都要输验证码**；接口测试走 8081 可跳过。两个实例共用同一个库，页面改完接口立刻能查到。
